# Machine Learning for Network Intrusion and Botnet Detection

General Assembly — Data Science & Machine Learning Capstone Project

## Overview

When I joined the course, I asked myself a question: how can I use machine learning to help my organization?

Working in cybersecurity, I have seen how limited staffing can make it difficult to monitor network activity and investigate potential threats. I wanted to explore whether machine learning could help identify suspicious traffic and give security analysts a better idea of where to focus their attention.

I approached this problem through two related projects:

1. **Network Intrusion Detection (UNSW-NB15):** Can a machine learning model distinguish normal network traffic from different types of attacks?
2. **Botnet Detection (CTU-13):** Can a model distinguish legitimate traffic from traffic generated by a botnet, using data that requires more exploration and preparation?

Both projects use supervised machine learning, meaning that the models learn from examples whose correct classifications are already known. They are research and learning experiments, not production-ready security tools.

## Understanding the problem

Whenever a device visits a website, sends an email or communicates with another device, it generates network traffic. This traffic can be summarized into records called **network flows**. A flow describes a communication using information such as how long it lasted, how many packets were exchanged and how much data was transferred.

A **Network Intrusion Detection System (NIDS)** monitors network activity to identify signs of potentially malicious behavior. A **botnet** is a group of compromised devices controlled by an attacker. Such devices may be used to send spam, launch attacks or communicate with the attacker's infrastructure.

The idea behind this project is to teach a computer to recognize patterns in these flow records. It receives a record and predicts one of two classes:

```text
Network flow → Prepare its characteristics → Machine learning model
                                                 |
                                      Normal or suspicious
```

The model does not read the contents of every packet, confirm that an incident occurred or automatically block a device. It classifies the flow using the characteristics available in the dataset.

### How do we know if the model works?

| Term | Meaning in this project |
|---|---|
| Training set | Examples the model uses to learn. |
| Validation set | Separate examples used to compare models and choose a candidate. |
| Test set | Held-out examples used to evaluate the chosen model. |
| Accuracy | The percentage of all predictions that are correct. |
| Precision | Of the flows flagged as malicious, how many actually have a malicious label? |
| Recall | Of all flows labeled malicious, how many does the model detect? |
| False positive (FP) | A normal flow incorrectly flagged as malicious — a potential false alarm. |
| False negative (FN) | A malicious flow incorrectly classified as normal — a missed detection. |
| False positive rate (FPR) | The percentage of normal flows incorrectly flagged. |

In cybersecurity, accuracy alone is not enough. A model that misses threats creates security risks, while a model that flags too much normal traffic can create unnecessary work for analysts.

## Part 1: Network intrusion detection

### Dataset and objective

The first project uses [UNSW-NB15](https://research.unsw.edu.au/projects/unsw-nb15-dataset), a dataset developed at UNSW Canberra in 2015. It contains normal traffic and different attack categories generated in a laboratory environment.

The dataset already provides extracted network features and labels, making it a useful starting point for learning how to develop and evaluate a machine learning classifier.

The objective was to classify a flow as either normal (`0`) or attack (`1`). The specific attack category was kept for later analysis, rather than given to the model as an input.

### Approach

- Explored the traffic, protocols, attack categories, missing values and feature distributions.
- Removed the record ID and label-related columns from the model inputs.
- Standardized numerical features and encoded categorical features using scikit-learn pipelines.
- Split the designated development dataset into 80% training and 20% validation, preserving the class proportions.
- Compared Logistic Regression, Decision Tree and Random Forest, including trees with restricted depths.
- Selected Random Forest, trained it on all 175,341 development records and evaluated it on the separate official test file.

Logistic Regression is a relatively simple classifier. A Decision Tree learns a series of decision rules, and a Random Forest combines the predictions of many trees. These three algorithms provided a useful comparison between simpler and more flexible models.

### Results

| Model | Validation accuracy |
|---|---:|
| Logistic Regression | 93.64% |
| Decision Tree (unrestricted) | 94.94% |
| Decision Tree (maximum depth 5) | 93.26% |
| Decision Tree (maximum depth 10) | 94.42% |
| Random Forest | **95.95%** |

Final Random Forest results on 82,332 test flows:

| Actual / predicted | Normal | Attack |
|---|---:|---:|
| Normal | 27,045 | 9,955 |
| Attack | 660 | 44,672 |

The model detected 44,672 of the 45,332 attack flows, achieving a recall of 98.54%. However, it also incorrectly flagged 9,955 normal flows. More than one quarter of the normal traffic was misclassified.

The accuracy fell from 95.95% on validation to 87.11% on the official test set. This was an important lesson: a strong validation result does not guarantee equally strong performance on new data.

### Error analysis

Of the 660 missed attack flows, 606 belonged to the **Fuzzers** category (approximately 92% of the missed attacks). Fuzzing involves sending unusual or unexpected inputs to software or services. The model detected approximately 90% of the Fuzzers flows, compared with 98.54% of attack flows overall.

The notebook also examines which features the Random Forest relied on, including packet time-to-live and traffic-rate-related characteristics. Feature importance describes the model's use of the data; it does not prove that a feature causes malicious behavior.

## Part 2: Botnet detection

### Why a second project?

The first dataset was already well prepared. I wanted to spend more time understanding the data, making decisions about its quality and testing the model in a way that better reflects how network traffic changes over time.

For this reason, I chose [CTU-13](https://www.stratosphereips.org/datasets-ctu13), specifically Scenario 1 (Neris botnet, Botnet-42 capture). This dataset contains recorded flows from a controlled malware experiment together with normal and background traffic.

### Understanding and preparing the data

The original capture contains 2,824,636 flows. Approximately 97.47% are labeled Background. Background does not mean verified normal traffic, so I did not treat it as a negative class.

For this experiment, I retained only the clearly labeled `From-Botnet` and `From-Normal` flows:

| Traffic type | Flows | Target |
|---|---:|---:|
| From-Botnet | 40,961 | 1 |
| From-Normal | 30,258 | 0 |
| Total | 71,219 | |

During exploratory data analysis (EDA), I examined traffic labels, protocols, durations, packet and byte counts, missing values and port distributions. I found that duration was highly skewed and that missing destination type-of-service (`dTos`) values occurred more frequently in botnet flows.

I also excluded source and destination IP addresses and ports from the first model to reduce the risk of learning shortcuts specific to this capture. The original labels were excluded from the inputs because they contain information about the correct answer. Nine flow characteristics remained, including duration, protocol, bytes, packets and connection state.

The objective was to learn traffic patterns rather than simply recognize the IP address of the known infected device.

### Chronological data splitting

Unlike the first project, I split the data by time instead of randomly mixing the network flows. This allows the model to learn from earlier traffic and be tested on traffic recorded later.

All three periods belong to 10 August 2011, within the same capture.

| Set | Time period | Flows |
|---|---|---:|
| Training | Before 14:00 | 51,293 |
| Validation | 14:00 to before 15:00 | 6,667 |
| Test | From 15:00 onward | 13,259 |

Missing numerical values were filled using medians learned from the training data, with additional indicators recording where values were missing. Numerical features were standardized and categorical features were encoded. These transformations were included in the model pipeline so that information from later periods was not used to calculate the preprocessing parameters.

### Model comparison

| Model | Validation accuracy |
|---|---:|
| Logistic Regression | 56.11% |
| Decision Tree (unrestricted) | 94.89% |
| Decision Tree (maximum depth 5) | 91.09% |
| Random Forest | **95.97%** |

Logistic Regression struggled to distinguish the two classes. The Decision Tree performed considerably better. Restricting its depth reduced the number of leaves from 2,545 to 29, although it also increased missed botnet flows. Random Forest provided the strongest validation performance and was selected for final testing.

### Final test results

The trained Random Forest was evaluated on the final time period without fitting it again.

| Actual / predicted | Normal | Botnet |
|---|---:|---:|
| Normal | 3,610 | 199 |
| Botnet | 517 | 8,933 |

The model correctly detected 8,933 of the 9,450 botnet flows, achieving 94.53% recall. It incorrectly flagged 199 normal flows and missed 517 botnet flows.

Although the final accuracy (94.60%) remained close to validation accuracy (95.97%), the percentage of missed botnet flows increased from 0.87% to 5.47%. This shows why it is important to examine the types of errors rather than accuracy alone.

### Feature importance and error analysis

Flow duration, total bytes and source bytes together accounted for approximately 81% of the model's impurity-based feature importance. These scores are descriptive and may favor certain types of features.

Further analysis of the mistakes revealed the following:

- 465 of the 517 missed botnet flows belonged to the UDP-DNS category. DNS is the service that translates domain names into IP addresses; UDP is a network transport protocol.
- 192 of the 199 false positives used destination port 53, commonly associated with DNS. Port information alone does not confirm the contents of a communication.
- The median duration of missed botnet flows was 0.0005 seconds, compared with 0.067 seconds for correctly detected botnet flows.
- Some smaller HTTP and SMTP categories had higher miss rates, even though DNS accounted for most errors by count.

These patterns suggest that short legitimate and malicious flows can have similar measurable characteristics. The model may need more information about the behavior of a device over time to distinguish them reliably.

## What the two projects taught me

The first project taught me how to build and compare classifiers, evaluate a separate test set and recognize the operational problem caused by false alarms.

The second project required more decisions about data preparation, ambiguous labels, missing values, feature selection and chronological evaluation. It also gave me a clearer understanding of the limitations of classifying individual network flows.

Random Forest was the strongest model by validation accuracy in both experiments. However, that does not mean it will always be the best algorithm for intrusion detection. The quality of the data and the evaluation procedure are just as important as the algorithm itself.

## Potential use in cybersecurity

A Security Operations Center (SOC) is responsible for monitoring, detecting and investigating security threats. A model like this could potentially support a SOC by prioritizing suspicious network activity and providing additional information for analysts to investigate.

The goal is not to replace analysts, but to help them focus their attention where it may be most valuable. The first experiment illustrates the risk of overwhelming analysts with false alarms, while the second shows that even a high-accuracy model can miss important activity.

The datasets contain high proportions of malicious traffic compared with what may be seen in an operational network. Precision can be much lower when genuine threats are rare, even if recall and the false positive rate remain unchanged. A flagged flow is also not necessarily a separate security incident or analyst alert.

No live SOC deployment, workload reduction, cost savings or financial return was measured in this project.

## Limitations and future work

- Both datasets are historical benchmarks. Performance on modern enterprise networks has not been established.
- The first dataset uses a laboratory environment, and its random internal split may place similar traffic patterns in both development subsets.
- The second model was trained and tested within one Neris capture. Background traffic was excluded, and the ability to generalize to different captures, networks or botnet families is unknown.
- The models use existing flow records, not live packet capture or real-time monitoring. A working NIDS would require additional engineering, integration, monitoring and testing.
- Future improvements could include more recent data, grouping flows by device or time window, DNS-specific information where available, and independent evaluation on additional captures.

Cross-scenario evaluation on another CTU-13 capture is a possible extension of the work, not a completed experiment.

## Final conclusion

The purpose of this capstone was to investigate whether machine learning could help identify malicious network traffic and, more importantly, to understand what is required to build and evaluate such a system responsibly.

Both experiments produced promising results on their respective test datasets, but both also revealed weaknesses. The first model generated a substantial number of false alarms, while the second struggled to distinguish certain types of botnet traffic from normal communication, particularly DNS-related flows.

For me, the most valuable outcome was learning how to approach a cybersecurity problem through data science, from understanding the data and preventing misleading model results to interpreting errors and recognizing the limits of the conclusions.

These projects provide a foundation for further work on machine learning-assisted intrusion detection. They are proofs of concept, not a replacement for existing security systems or the judgment of cybersecurity professionals.
